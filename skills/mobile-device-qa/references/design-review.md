# 기준 앱·Figma와 픽셀 단위 디자인 검수

- Author: JunyoungJung
- Created: 2026-10-22
- Updated: 2026-10-27

기존 앱 또는 Figma 디자인과 새 코드의 실제 화면을 같은 크기로 비교하고 불일치 수정·재촬영·보고까지 요청받았을 때 읽는다. 비교 도구는 PNG의 차이를 계산하며 화면 상태·실제 실행 대상·코드 반영·종합 판정은 메인이 확인한다. 읽기 전용 요청이면 코드·보고서·이미지·임시 파일을 만들지 않고 확보된 자료의 검토 결과와 미확인을 반환한다.

## 기준과 캡처 조건 고정

프로젝트 전용 저장소의 기존 디자인 정책·기준·흐름을 먼저 확인한다. 화면별 `screen_id`와 다음 정보를 `design_plan`으로 실행 담당자에게 전달한다.

| 항목 | 확인할 내용 |
|---|---|
| 기준 출처 | `app` 또는 `figma`, 기준 앱 ID·빌드·소스/산출물 식별 또는 Figma 파일·frame/node ID·버전/확인 시점·원본 링크 |
| 수정 대상 | 프로젝트·타깃·앱 ID·빌드·configuration/SDK variant, 현재 설치와 소스의 일치 근거, 수정 허용 범위 |
| 화면 크기 | 동일 모델·화면 방향, viewport의 pt/dp 또는 Figma frame 단위 크기, pixel scale, PNG의 실제 width×height, safe area·시스템 바 포함 범위 |
| 렌더링·상태 | OS, theme, locale, Dynamic Type/글꼴 크기·font asset/weight, 표시 데이터·선택 탭·정렬·스크롤·키보드·팝업·애니메이션·재생/정지·컨트롤 상태 |
| 수집·판정 | 기준·최초 수정 전·최종 수정 후 체크포인트, 변경할 수 없는 기준, 사전 정의한 제외 영역·이유, 코드 수정·준비 작업 승인과 종료 조건 |

같은 픽셀 수만으로 같은 디바이스·논리 크기·상태라고 판단하지 않는다. 앱 간 비교는 가능하면 **같은 물리 기기 또는 같은 Simulator·runtime에서 순차 촬영**한다. 같은 앱 ID의 기준/신규 빌드 교체가 필요하면 설치·자료 보존·인증 영향을 확인하고 기존 준비 절차로 인계한다. QA를 위해 기존 다운로드·설정을 지우거나 계정 전환을 임의 수행하지 않는다. 이미 허용된 준비·수정 범위를 다시 승인받지 않는다.

### 기존 앱 기준

기준 앱의 지정 화면과 상태를 확인해 원본 PNG를 촬영한 다음, 새 코드가 반영된 앱에서 같은 화면을 촬영한다. 실기기는 기존 `agent-device` 세션을, Simulator는 [Simulator QA](simulator.md)의 `simctl` 원본 캡처를 사용할 수 있다. 명시적 대상 ID·검증한 출력 경로를 사용하며 `agent-device` 미설치로 디자인 검수를 차단하지 않는다. 현재 캡처 명령의 저장 인자가 불명확할 때만 해당 도구의 도움말을 확인한다. 두 대상의 소스·설치·빌드·촬영 시점을 따로 기록한다. 이전 앱·중간 빌드의 이미지를 마지막 수정 빌드의 결과로 사용하지 않는다.

### Figma 기준

준비된 Figma 스킬·연결 도구에서 지정 frame의 크기·하위 요소·spacing·typography·color·asset과 PNG export 지원을 확인한다. **정확한 frame을 실제 viewport×scale에 대응하는 PNG로 내보내며**, 브라우저 확대율·에디터 chrome·selection outline이 포함된 화면 캡처를 기준으로 사용하지 않는다. 비정수 배율·크기·font·색공간을 확인하지 못하면 정확 비교를 `준비 필요`로 남긴다. Figma 파일/노드·버전·export scale·시점과 로컬 PNG의 hash를 연결한다.

Figma PNG는 디자인 기준이며 실앱 캡처·동작 증거가 아니다. 새 코드 화면은 지정 빌드가 실행 중인 실기기 또는 Simulator에서 별도로 촬영하고 대상 종류를 기록한다. 픽셀 차이를 없애려고 기준 frame·디자인 토큰·기준 앱을 수정하지 않는다. Figma 변경이 별도로 요청되지 않았다면 읽기·export만 수행한다. 연결·원본 export가 없으면 실제 준비 사항을 알리고 다른 독립 항목을 계속한다.

## 동일 크기 PNG의 겹침과 차이 계산

캡처 원본과 파생 이미지는 **선택한 저장 폴더 안의 검증된 대상 프로젝트 작업 경로**에 둔다. 화면·대상·빌드·시도별로 경로를 나누고 최초 수정 전 이미지를 보존한다. 자동 resize·회전·정렬·blur·crop으로 차이를 숨기지 않는다. 부분 영역 비교가 필요하면 원본 전체를 유지하고 두 이미지에서 같은 고정 좌표·이유를 사전에 기록하며 전체 화면 일치로 표현하지 않는다.

기존에 준비된 Python 3.11–3.13과 `requirements.txt`의 Pillow·numpy로 다음 도구를 실행한다. 도구가 없으면 설치를 자동 수행하지 않고 `준비 필요`로 남긴다. 변수는 실제 확인한 로컬 파일과 **선택 폴더 안의 비어 있는 시도별 출력 경로**다.

도구는 단일 프레임 SDR PNG의 8비트 이하 입력을 지원한다. 16비트·HDR 색 청크·APNG·회전 메타데이터는 자동 변환하지 않고 오류로 반환한다. 지원되는 원본 PNG를 다시 확보하며 이 제한을 앱의 디자인 불일치로 판정하지 않는다.

```bash
python3 -B "$QA_SKILL_DIR/scripts/compare_screenshots.py" \
  --reference "$REFERENCE_PNG" \
  --candidate "$CANDIDATE_PNG" \
  --output-dir "$PIXEL_OUTPUT_DIR"
```

- 크기가 다르면 실패하며 파일을 맞추기 위해 이미지 크기를 바꾸지 않는다. 같은 실제 viewport·scale로 다시 확보한다.
- 기본 비교는 색 메타데이터가 같은 원본 RGBA 픽셀을 대상으로 한다. ICC/색 정보가 다르면 준비를 보완한다. 명시적인 sRGB 비교가 필요한 경우에만 `--normalize-srgb`를 사용하고 변환·무프로파일 가정·원본 결과와 변환 후 결과를 보고한다. 변환 후 같은 픽셀이라는 사실을 원본 픽셀 일치로 표현하지 않는다.
- 도구는 candidate 비율 25%·50%·75%의 `overlay-25.png`·`overlay-50.png`·`overlay-75.png`, 가시적인 `diff.png`, 불일치 픽셀을 흰색으로 표시한 `mismatch-mask.png`, `comparison.json`을 생성한다. 시각 산출물은 제외 영역을 포함한 전체 이미지이며 `mismatch-mask.png`도 제외 마스크 적용 전 결과다. 메인은 원본 두 장과 겹침·차이를 직접 열어 확인한다. 입력 hash·크기, 비교/제외 픽셀 수, 변경 픽셀·비율, 최대 채널 차이·평균 절대 오차, 불일치 bounding box와 산출물 경로를 대조한다.
- `raw_exact`·`compared_exact`는 도구의 해당 이미지·비교 범위 결과다. 도구 종료 코드 0은 비교 실행 완료이며 픽셀 일치나 디자인 종합 통과를 뜻하지 않는다. JSON의 실제 결과와 조건을 함께 읽는다. 누락·실패를 차이 0으로 채우지 않는다.

### 동적 영역과 개인정보

시계·영상 프레임·서버가 바꾸는 숫자 등 재현할 수 없는 영역은 **비교 전에** 좌표·이유·마스크 ID를 정의한다. 필요한 경우 동일 크기의 이진 L-mode PNG를 `--mask "$EXCLUSION_MASK_PNG"`로 전달한다. 검정 0은 비교, 흰색 255는 제외이며 전체 제외 마스크는 허용하지 않는다. 비교 후 차이를 보고 마스크를 넓혀 통과를 만들지 않는다. 레이아웃·폰트·텍스트·아이콘·safe area·컨트롤 같은 검수 대상을 동적 영역으로 숨기지 않는다.

마스크가 있으면 **제외 영역 밖** 결과만 판정하며 전체 화면 픽셀 일치라고 보고하지 않는다. 제외 영역도 전체 겹침·원본에서 육안 확인하고 검수 대상이 가려지면 해당 부분은 `미검증`으로 남긴다. 비밀 입력 정리 미확인 기기는 일반 캡처를 재개하지 않는다. 검은 보호 캡처·빈 이미지·한쪽 자료 누락은 두 화면의 일치 근거가 아니다.

원본 비교는 선택 폴더 안의 비공개 경로에서 수행한다. 공유 보고서에는 필요한 사본만 마스킹해 첨부하고, 마스킹된 사본을 원본 픽셀 판정에 사용하지 않는다. overlay/diff에도 두 원본의 개인정보가 드러날 수 있으므로 공유 전 함께 확인한다. 보호 해제는 기존 승인·프로젝트 검수 설정과 종료 후 복구 조건을 따른다.

## 불일치 찾기 → 코드 수정 → 같은 조건에서 재검증

1. 최초 수정 전에 기준과 현재 구현의 PNG·hash·조건을 확보하고 첫 비교를 보존한다. 크기·state·font·데이터·색공간이 다르면 구현 결함과 준비 차이를 먼저 구분한다. 자동 보정으로 조건 차이를 지우지 않는다.
2. 겹침의 이중 윤곽과 diff/bounding box에서 간격·정렬·frame·safe area·font/weight/line height·색/alpha·border/shadow·아이콘/asset·잘림·상태 차이를 찾는다. 각 불일치를 안정적인 항목 ID, 실제 이미지 좌표와 확인된 scale의 pt/dp 대응, 기대/관찰, 원본 근거로 기록한다. bounding box는 차이의 위치이지 코드 원인 판정이 아니다.
3. 실제 소비 화면·Figma 요소·레이아웃/토큰/asset의 원천 코드를 추적한다. **수정이 승인된 요청이면 메인이 새 코드만 수정**하고, 캡처 담당자는 코드·기준·기대값을 바꾸지 않는다. 화면 통째 교체·이미지 덧씌우기·Dynamic Type/접근성/기능 비활성화로 차이를 없애지 않는다. 승인 범위를 벗어난 정책 결정은 해당 논점만 확인한다.
4. 프로젝트 지침에 맞는 검사·빌드·설치를 수행하거나 준비 담당자에게 인계한다. 선택한 저장 폴더의 경계·프로젝트/호스트 산출물 정책·로그·기기 점유 규칙을 유지한다. 앱 반영 확인 뒤 같은 기기·상태에서 새 파일로 재촬영하고 **고정한 기준·마스크·조건으로** 비교한다. 빌드·설치 실패나 캡처 불가이면 최종 수정 후를 `미검증`으로 남긴다.
5. 원인이 확인된 불일치를 수정하고 새 근거로 검증하는 과정을 계속한다. 새 불일치·회귀도 함께 확인한다. 같은 원인의 실패에서 새로운 근거·수정 없이 재캡처·재실행을 반복하지 않으며 차단·미결 사항을 기록한다. 이전 성공 캡처를 최종 변경 빌드의 결과로 대체하지 않는다.
6. 메인이 변경 픽셀 0 여부와 원본·상태·빌드·제외 범위를 대조하고 디자인 항목별로 최종 판정한다. 허용 편차가 별도로 합의됐다면 출처·수치·범위를 기록해 `허용 편차 내 일치`와 `완전 픽셀 일치`를 구분한다. 임의의 점수·평균 오차·변경 비율 합격선을 만들지 않는다. 기능·동적 동작·접근성·다른 기기/OS의 통과는 별도 근거가 필요하다.

## 구간 입력과 반환

`design_plan`은 `reference`(kind·source_ref·frame/version 또는 앱 빌드), `screens`(screen_id·viewport/scale·상태·촬영 역할·체크포인트), `mask_ref`(없으면 null), `color_policy`, `fix_scope`를 담는다. 확인하지 않은 값은 null/사유로 전달하며 의존하는 캡처·수정 전에 확보한다. 실제 기기 ID·세션은 기존 로컬 `execution` 문맥에만 둔다.

실행 담당자는 `design_captures`에 실제 촬영한 각 `screen_id`, `role`(`reference`·`candidate_before`·`candidate_final`), `target_id`, `app_build`, `image_path`, `sha256`, `observed_at`, `pixel_size`, `viewport`, `scale`, `conditions_match`(true/false/null), `note`를 반환한다. 캡처 직후 파일의 SHA-256을 기록하고 메인은 비교 JSON의 입력 hash와 대조한다. hash 미수집은 null/사유로 남겨 비교 전에 확인하며 파일이 바뀌었으면 이전 캡처의 근거로 사용하지 않는다. 누락·불일치·부분 실행을 별도로 기록하며 촬영하지 않은 항목을 만들지 않는다. Figma export는 메인이 출처를 확인해 기준으로 연결하고 기기 촬영 결과로 위장하지 않는다. 종합 판정·원본 확인·비교 도구 실행·수정은 메인이 맡는다.

프로젝트 전용 Library 저장소에는 기준 출처/버전·기기 조건·마스크 정책·재사용 흐름·확인한 원인과 코드 위치·다음 재검증 조건을 기록한다. PNG·diff·영상·실행 JSON은 선택한 저장소의 근거에 유지하고 관련 보고서 항목 ID/로컬 근거를 연결한다. Figma 변경·OS·font·viewport·asset·앱 소스가 영향을 줄 때 관련 기록을 재검증한다.

## 최종 리포트

[기존 보고 규칙](reporting.md)을 유지하고 기준 PNG와 최초 수정 전/최종 수정 후 2열, 최종 25/50/75% 겹침, 수정 전/최종 diff를 본문에 첨부한다. 중간 시도는 선택한 저장소의 원본 이력으로만 보존한다. 대표 실제 조작 GIF는 별도로 첨부하며 정지 이미지를 반복한 GIF로 실제 동작을 증명하지 않는다.

리포트에는 기준 종류·파일/node/version·앱 빌드·기기/OS·viewport/scale·원본 픽셀 크기·촬영 시점·hash, 제외/색변환 조건, 수정 전후 수치, 불일치 ID·위치·수정 코드·재검증 결과·남은 차이·판정과 근거를 남긴다. 검수하지 못한 대상도 표에서 빼지 않고 사유를 표시한다. 픽셀 비교 파일 생성·단일 화면 일치·전체 기능 동등성은 각각 구분한다.
