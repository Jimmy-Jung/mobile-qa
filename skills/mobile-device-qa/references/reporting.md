# 증거 수집과 Markdown 보고

- Author: JunyoungJung
- Created: 2026-10-22
- Updated: 2026-10-22

QA 계획에서 캡처 구간을 정할 때와 최종 보고서를 작성할 때 읽는다. 읽기 전용·파일 작성 금지 요청에서는 보고서·첨부·임시 파일을 만들지 않고 확보된 사실과 미확인·미저장 사유를 응답으로 전달한다. 승인·기기 점유·판정 경계는 [스킬 본문](../SKILL.md)을 따른다.

## 스크린샷·GIF 수집과 수정 비교

- QA 시작 시 항목별 결과 화면과 대표 조작 흐름의 녹화 구간을 정한다. 일반 QA에도 스크린샷과 최소 한 개의 GIF를 포함하며, 전환·애니메이션이 검증 대상이면 해당 동작도 담는다. 캡처는 체크포인트에서 수행하고 매 조작마다 반복하지 않는다. 성능 계측용 실행과 시각 자료 수집용 실행은 분리한다.
- 다중 대상·수정 전후 비교는 촬영 전에 비교 목적과 필요한 동일 조건을 체크포인트에 적고, 캡처 시 같은 화면·상태와 비교 축 이외의 입력·데이터·방향·시나리오가 맞는지 확인한다. 동작 비교라면 선택 상태·입력값·진행 단계·컨트롤 표시를 맞추고, 레이아웃 참고 비교라면 비교 영역과 제외할 차이를 정한다. 조건이 다른 자료는 표 안에도 `참고 비교`와 차이를 표시하며 동작 동등성 근거로 쓰지 않는다. 각 대상의 앱 버전·빌드, 디바이스 모델, 플랫폼·OS, 촬영 시점을 기록한다. 사용자가 비교 대상으로 지정한 버전은 중간 수정본이 아니므로 모두 유지하며, 최초 수정 전·최종 수정 후의 선택은 대상별로 적용한다.
- 수정 요청이 있거나 QA 중 수정 범위가 추가되면 **해당 항목을 처음 수정하기 전에** 결함·기존 상태의 스크린샷을 보존한다. 비교할 화면·기기·방향·입력·데이터·시나리오를 맞추고 전후 빌드와 촬영 시점을 기록한다. 조건이 달라졌다면 비교 한계를 명시한다. 수정 전 증거가 없으면 수정 후 화면을 재사용하거나 합성하지 말고 `수정 전 캡처 미확보`로 남긴다.
- 수정·재검증을 여러 번 반복해도 최초 수정 전 이미지는 유지한다. 수정 후 이미지는 **마지막 코드 변경이 반영된 앱 빌드에서 해당 항목을 재검증한 실제 화면**만 선택한다. 이전 성공 화면을 최종본으로 쓰지 않는다. 최종 재검증이 실패했다면 실패 화면과 판정을 그대로 첨부하고, 실행하지 못했다면 `최종 수정 후 미검증`으로 표시한다.
- 중간 시도의 캡처·녹화·실패 이력은 로컬 원본 근거로 보존하되, 수정한 항목의 시각 자료는 최종 리포트 본문과 배포용 `assets/`에 최초 수정 전·최종 수정 후 자료만 포함한다. 수정 항목의 GIF도 최종 재검증 구간을 사용한다. 동작 비교가 필요하면 최초 수정 전 GIF를 함께 첨부할 수 있으나 중간 GIF는 제외한다. 수정하지 않은 QA 항목의 결과 자료도 함께 첨부한다.
- GIF는 실제 녹화 또는 시간순 연속 캡처에서 생성하고 원본을 보존한다. 준비된 변환 도구를 사용하며, 단일 스크린샷을 반복한 GIF나 수정 전후 정지 화면을 이어 붙인 자료를 동작 증거로 쓰지 않는다. 캡처·녹화·변환이 불가능하면 해당 첨부 위치에 이유와 준비 사항을 적고 확보한 원본 영상 등을 연결한다. 누락된 자료를 생성·확인했다고 보고하지 않으며 그 자료가 필요한 검증은 `미검증` 또는 `준비 필요`로 남긴다.

## 결과 보고

요청한 검증 항목별로 다음 정보를 간결하게 남긴다. 프로젝트의 기존 결과 형식을 사용하더라도 스크린샷·GIF 첨부, 수정 전후 2열 비교와 다중 대상 N열 비교는 유지한다.

| 항목 | 실행 도구 | 기대 결과 | 실제 관찰 | 판정 | 명령 소요 시간 | 근거 |
|---|---|---|---|---|---|---|

- 판정은 `통과`, `실패`, `미검증`, `준비 필요`를 구분한다. 요청된 항목이 실행되지 않았으면 누락하지 않는다.
- 기기 모델·OS·앱 빌드·실행 도구와 버전·시나리오, 전체 경과 시간, 전환/복구 이력과 재실행 결과를 함께 기록한다. 기기 고유 식별자나 원문 로그를 요약에 노출할 필요는 없다.
- 분리 실행했다면 호스트·버전, 요청 모델과 실제 모델·추론 강도 및 확인 출처, 메인에 반환한 구간·예외·승격 이유를 함께 남긴다. 설정 요청만 확인했다면 실제 적용까지 검증했다고 보고하지 않는다. 단독 실행으로 전환했다면 그 이유를 남긴다. 모델 변경의 정확도·속도 개선을 주장할 때는 [모델 정책의 회귀 평가](model-policy.md#신모델-회귀-평가)를 적용한다.
- 적용한 프로젝트 정책·지식의 ID와 출처, 이번에 갱신한 Mac QA 전용 저장소의 문서·상태 또는 미저장 사유를 남긴다. 로컬 저장소 내용을 공유 보고서로 통째로 복사하지 않으며 기록 완료를 정책 승인이나 재검증 완료로 표현하지 않는다.
- 재사용한 흐름의 ID·revision, 새로 저장한 실행 파일·계약·카탈로그 위치, 재검증 필요 항목을 요약한다. 저장이 끝나지 않았으면 사유와 남은 상태를 적는다. 저장 완료와 실기기 검증 완료를 구분한다.
- 스크린샷·GIF는 아래 형식으로 본문에 표시하고, 원본 녹화·상태 로그의 로컬 경로는 보조 근거로 연결한다. 경로 목록만으로 시각 자료 첨부를 대신하지 않는다. 근거를 직접 확인하지 않았다면 확인 완료라고 쓰지 않는다.
- 결과는 실제 시험한 플랫폼·기기·빌드에만 적용한다. 다른 플랫폼의 문서상 지원이나 한 기기의 성공으로 범위를 넓히지 않는다.
- 누락 정보나 필요한 사용자 조치는 대화에서 짧게 설명한다. 질문용 모달을 띄우지 않는다.

## 시각 자료 첨부 형식

단일 대상의 수정 없는 QA는 항목별 스크린샷과 대표 흐름 GIF를 `![설명](assets/파일명)`으로 삽입한다. 단일 대상의 수정한 항목은 아래처럼 **수정 전 / 최종 수정 후의 2열 표**를 사용한다. 각 항목에 관찰 차이·최종 판정과 전후 빌드·촬영 시점을 적는다. 아래 경로는 형식 예시이며 실제로 확보한 첨부 파일로 바꾼다.

```markdown
### QA-01 수정 전후 비교

| 수정 전 — 최초 상태 | 수정 후 — 최종 재검증 |
|---|---|
| ![QA-01 최초 수정 전](assets/QA-01-before.png) | ![QA-01 최종 수정 후](assets/QA-01-after-final.png) |

![QA-01 최종 재검증 동작](assets/QA-01-after-final.gif)
```

동일 화면의 다중 대상 비교는 **N개 대상 → N개 스크린샷 열**로 배치한다. 화면·상태별로 표를 만들고 모든 표에서 대상 순서를 유지한다. 헤더에는 비교 축의 실제 값(앱 버전·빌드, 디바이스 모델, 플랫폼·OS 등)을 넣어 대상을 구분한다. 캡처하지 못한 대상도 열을 유지하고 해당 셀에 `미검증`·`준비 필요`와 사유를 적는다. 아래는 3개 대상을 비교하는 형식 예시이며 대상 수에 맞게 열을 늘리거나 줄인다.

```markdown
### QA-02 동일 화면·상태 비교

| 버전 A · 디바이스 A · 플랫폼 A | 버전 B · 디바이스 B · 플랫폼 B | 버전 C · 디바이스 C · 플랫폼 C |
|---|---|---|
| ![QA-02 대상 A](assets/QA-02-target-a.png) | ![QA-02 대상 B](assets/QA-02-target-b.png) | ![QA-02 대상 C](assets/QA-02-target-c.png) |
```

다중 대상 비교에 수정 전후 비교도 포함되면 `대상 A 최초 수정 전 | 대상 A 최종 수정 후 | 대상 B 최초 수정 전 | 대상 B 최종 수정 후 | …`처럼 **대상별 두 열을 인접하게 배치한 2N열 표**를 사용한다. 각 대상의 중간 수정본은 제외한다. GIF의 대상·빌드도 명확히 표시하며 다른 대상의 스크린샷·GIF로 누락 근거를 대신하지 않는다.

## 픽셀 디자인 검수 보고

디자인 일치 요청은 [디자인 검수](design-review.md)의 조건·수치·판정 기준을 적용한다. 화면별 기준 앱 빌드 또는 Figma 프레임·버전·출처, 기준/후보 PNG의 실제 픽셀 크기와 논리 크기·배율, OS·테마·폰트·상태, 색 처리와 제외 영역을 기록한다. 미확인 값은 추정으로 채우지 않는다.

고정된 기준 이미지를 먼저 표시하고 후보의 최초 수정 전 / 최종 수정 후는 기존 2열 비교를 유지한다. 최종 겹침 3종과 최초/최종 차이 이미지, 각각의 `comparison.json`을 연결한다. 전체 리포트의 다중 대상 순서는 유지하며 중간 시도의 파생 이미지도 배포용 첨부에서 제외한다. 아래는 형식 예시다.

```markdown
### DESIGN-01 목록 화면

기준: 확인한 앱 빌드 또는 Figma 프레임·버전·출처. 촬영/내보내기 조건과 시점, 색 처리·제외 영역 및 사유를 기록한다.

![DESIGN-01 고정 기준](assets/DESIGN-01-reference.png)

| 최초 수정 전 | 최종 수정 후 |
|---|---|
| ![최초 후보](assets/DESIGN-01-before.png) | ![최종 후보](assets/DESIGN-01-after-final.png) |
| ![최초 차이](assets/DESIGN-01-before-diff.png) | ![최종 차이](assets/DESIGN-01-final-diff.png) |

| 최종 후보 25% 겹침 | 최종 후보 50% 겹침 | 최종 후보 75% 겹침 |
|---|---|---|
| ![25%](assets/DESIGN-01-final-overlay-25.png) | ![50%](assets/DESIGN-01-final-overlay-50.png) | ![75%](assets/DESIGN-01-final-overlay-75.png) |

| 비교 | 원본 RGBA 완전 일치 | 비교 범위 일치 | 변경 픽셀/비교 픽셀 | 변경 비율 | 최대 채널 차이 | 평균 절대 오차 | 제외 픽셀 | 변경 bbox |
|---|---|---|---|---|---|---|---|---|

| 차이 ID | 위치·근거 | 확인한 원인 | 수정 파일·내용 | 최종 상태·남은 차이 |
|---|---|---|---|---|

[최초 비교 수치](assets/DESIGN-01-before-comparison.json) · [최종 비교 수치](assets/DESIGN-01-final-comparison.json)
```

실제 수치를 첫 비교와 최종 비교의 행에 넣고 bbox는 원본 픽셀 좌표와 끝점의 포함 여부를 명시한다. pt/dp 환산은 확인한 배율이 있을 때만 적는다. 제외 영역이 있으면 `비교 범위 일치`, 색 변환을 했다면 `정규화 후 일치`로 범위를 표시한다. 사전 승인된 허용 편차만 충족한 결과는 `허용 편차 내 일치`이며 원본 픽셀 완전 일치로 보고하지 않는다. 크기·상태·색 조건 불일치, 캡처 실패나 보호된 검은 화면은 통과 근거가 아니다. 비교 도구의 종료 코드 0도 일치 판정이 아니다.

수정하지 않은 검수는 기준/현재 후보와 현재 겹침·차이·수치를 표시하고 수정안·남은 불일치를 보고한다. 수정 후 화면을 만들어 넣지 않는다. 실제 조작 GIF는 기존 기준대로 별도 첨부하며 정지 이미지 겹침을 동작 GIF로 대신하지 않는다.

## 첨부 확인

- Markdown 이미지 경로는 리포트 기준 상대 경로를 사용하고 공백은 `%20`으로 인코딩한다. Obsidian 전용 임베드는 사용하지 않는다. 첨부 불가 시 이미지 문법과 빈 파일을 남기지 말고 해당 셀·위치에 미확보 사유를 쓴다.
- 첨부본에서 계정·토큰·개인정보를 가리고, GIF는 모든 프레임을 확인한다. 마스킹이 검증 대상을 가리면 해당 한계를 명시한다.
- 전달 전 메인이 스크린샷을 열고 GIF를 재생해 내용과 빌드를 대조한다. 첨부 파일 존재·상대 경로·비교 대상 수에 맞는 열 배치·대상별 근거 대응과 중간본 제외 여부를 확인하고 리포트 위치를 사용자에게 알린다. 실제 뷰어에서 확인하지 않았다면 렌더링·재생 검증까지 완료했다고 보고하지 않는다.
