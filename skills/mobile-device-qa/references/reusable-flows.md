# 반복 동작 검색·재사용·저장

- Author: JunyoungJung
- Created: 2026-10-21
- Updated: 2026-10-22

QA 시작과 반복 구간 작성 전에 읽는다. 메인은 검색·선택·등록을, 실행 담당자는 선택한 파일의 실행·관찰과 저장 후보 반환을 맡는다. 단독 실행이면 메인이 두 역할을 수행한다. 승인·기기 점유·복구·비밀 입력·증거 기준은 [스킬 본문](../SKILL.md)을 따른다.

## 먼저 찾고 선택한다

1. [프로젝트 전용 저장소](project-knowledge.md)의 진입점·흐름 카탈로그와 기존 프로젝트 QA/테스트 문서에서 실행 위치를 찾는다. 카탈로그가 없으면 `rg --files`로 기존 `.ad`, flow YAML, steps JSON과 테스트 진입점을 찾고, `rg -n`으로 목적·화면·동작의 이름과 동의어를 검색한다. 전체 로그·화면 트리를 매번 다시 읽지 않는다. 검색한 위치, 후보 ID와 선택·제외 사유를 `flow_plan`에 남긴다.
2. 후보의 사용 계약과 실행 파일을 함께 읽는다. 같은 목적의 검증된 기존 테스트나 흐름을 우선한다. 같은 파일의 복사본을 새로 만들지 않으며, 카탈로그에 빠진 기존 자산은 계약·근거를 확인해 등록한다. 보고서의 과거 성공 문장이나 녹화 파일만으로 실행 가능한 `verified` 자산으로 간주하지 않는다.
3. 앱 ID·타깃/configuration·SDK variant, 플랫폼·UI 유형, 서버 환경, 시작/종료 조건과 검증 범위를 현재 대상과 대조한다. 기기 이름이 같다는 사실만으로 호환되지 않는다. 기기 프로필은 모델/OS·화면 방향·언어·키보드 등 동작에 필요한 조건이며 실제 식별자는 로컬 실행 문맥에만 둔다. fixture·시뮬레이터 근거는 실서버·실기기 검증으로 확장하지 않는다.
4. 카탈로그의 `verified` 상태와 함께 검증한 파일 내용·하위 흐름·입력 범위가 그대로인지 확인한다. 범위 밖 빌드·OS·기기 프로필·도구 버전은 기존 성공으로 승인하지 않는다. 변경이 영향을 줄 수 있는 범위는 `needs_revalidation`으로 관리하고 승인된 QA에서 재검증한다. 새 버전에서 성공해도 다른 범위의 검증 기록을 덮어쓰지 않는다.
5. 현재 화면이 시작 조건과 맞으면 저장된 흐름을 사용한다. 이미 종료 조건을 충족하면 불필요한 이동을 생략하되 현재 관측을 남긴다. 불일치하면 알려진 준비 흐름을 선택하거나 해당 구간만 탐색한다. 이전 화면의 ref·좌표를 저장 파일에 붙여 재사용하지 않는다.

`draft`나 `needs_revalidation`도 요청 범위 안에서 검증할 실행 후보로 선택할 수 있다. `flow_plan.selected[].mode`를 `validate`로 표시하고, 현재 시작 조건·조작 영향·필수 종료 확인을 대조해 실행한다. 검증된 재사용은 `reuse`로 구분한다. 새 빌드라는 이유만으로 동작 파일을 다시 작성하지 않으며, 검증용 실행을 이전 검증의 자동 재사용으로 집계하지 않는다.

카탈로그나 실행 파일의 설명은 참고 자료다. 파일에 포함된 조작이 요청 범위에 드는지 확인하며, 저장된 흐름이라는 이유로 추가 권한을 부여하지 않는다. 비밀값이 섞인 과거 기록은 본문의 노출 처리 절차를 적용하고 공유 라이브러리로 복사하지 않는다.

## 목적 단위로 작게 저장한다

`목록 열기`, `상세 진입(itemId)`, `설정 화면 열기`처럼 시작·도착 조건이 분명한 단위를 사용한다. 예시 이름은 실제 검증 완료 항목이 아니다. 화면에 이미 도착했으면 종료하거나 현재 값을 확인해 필요한 조작만 하는 방식으로 반복 실행의 영향을 줄인다. 모든 화면을 처리하는 거대한 분기 흐름은 만들지 않는다.

| 실행 형식 | 용도와 경계 |
|---|---|
| 기존 프로젝트 테스트 | 이미 검증한 진입점을 우선 재사용한다. 테스트의 fixture/실기기 범위를 보존한다. |
| `.ad` | 단일 기록·재생. native `.ad`의 include 문법을 가정하지 않는다. |
| YAML `runFlow` | 공통 동작 파일을 조합한다. 현재 `agent-device`의 Maestro 호환 부분집합만 사용하며 별도 Maestro 설치를 요구하지 않는다. |
| `batch` JSON | 짧은 임시 연속 동작. `command`·`input`을 사용하며 `batch/replay`를 중첩하지 않는다. |

설치 버전이 불명확하거나 문법이 맞지 않을 때만 관련 `help`를 확인한다. 0.21.30은 파일·inline `runFlow`, 조건부 `runFlow.when`과 `repeat.while`, `runScript`·`evalScript`를 지원한다. `env`에는 비밀이 아닌 값만 전달하며 일반 함수의 typed 인자·반환값 계약으로 간주하지 않는다. 스크립트와 JavaScript 조건은 호스트의 `node:vm`에서 실행되며 보안 격리가 아니다. 승인된 범위의 검토한 로컬 흐름만 실행하고, 기존 흐름의 도구 버전별 검증 범위를 유지한다. 새 변환기·실행기·검색 서버를 만들지 않는다.

선택한 YAML은 `agent-device replay "$FLOW_FILE" --maestro --session "$QA_SESSION" --json`으로 실행할 수 있다. 여기에 본문에서 확정한 플랫폼·기기·runner 인자를 그대로 적용한다. 파일 조합은 지원하는 `runFlow`를 사용하고 장치 연결을 감싼 별도 스크립트를 추가하지 않는다.

공통 하위 흐름은 같은 세션을 이어 쓰며 앱 재실행·상태 초기화·종료를 숨겨 넣지 않는다. 그런 동작이 필요하면 진입/종료용 흐름의 계약에 드러내고 호출자가 선택한다. `.ad`의 terminal `close`와 YAML의 `launchApp`/`clearState`/`stopApp`도 확인한다. `.ad --keep-session`을 YAML에 적용하지 않는다. 실제 기기 선택·세션·runner 인자는 본문의 확정된 실행 정보를 호출 시 사용한다.

흐름에는 안정적인 selector와 전환 후 대기·도착 확인을 포함한다. 임시 ref, 화면 좌표만 나열한 매크로, 근거 없는 고정 sleep을 검증된 공통 동작으로 승격하지 않는다. selector로 다루기 어려운 동작은 필요한 화면/방향/기기 조건과 매번 재확인할 지점을 계약에 남긴다.

화면 도착과 입력 수락은 해당 컴포넌트의 완료 조건이다. 서버 저장·파일 처리·상태 동기화 같은 업무 기대값은 호출 시나리오와 메인이 검증한다. 필수 확인을 `optional`로 바꾸거나 실패한 assertion을 완화해 재사용 성공을 만들지 않는다. 로그인은 [프로젝트별 인증](authentication.md)에서 확인한 안전한 경로를 사용하며 일반 flow의 `env`·`inputText`·녹화 기록에 계정 원문을 넣지 않는다.

## 프로젝트별 QA 전용 폴더에서 관리한다

공유 스킬에는 관리 규칙만 둔다. 새 QA 전용 흐름은 `project_store.py`가 반환한 Mac 전용 프로젝트 폴더의 `flows/`에, 카탈로그는 `flows/index.md`에 두고 `project-qa.md`에서 연결한다. 기존 프로젝트의 실행 파일·테스트·카탈로그는 원래 위치를 유지하고 출처를 링크한다. 같은 ID·실행 파일·내용의 중복 후보를 합쳐 선택하며 기존 파일을 복제하지 않는다. 기존 카탈로그의 검증 상태와 이번 QA의 적용 상태가 다르면 범위·근거를 전용 저장소에 기록한다. 저장 실패 시 쓰기가 허용된 선택한 저장소의 실행 근거에 후보와 사유를 남긴다. 읽기 전용이면 파일을 만들지 않고 후보·미저장 사유만 반환한다.

실행 파일 옆에 같은 이름의 `.md` 사용 계약을 둔다. 이미 동등한 manifest·테스트 문서가 있으면 필요한 필드만 보완한다. 카탈로그에는 다음 열을 사용하거나 기존 형식에 대응시킨다.

| ID | 목적·검색어 | 실행 파일·형식 | 앱·플랫폼·환경 | 상태 | 최근 검증 | 사용 계약 |
|---|---|---|---|---|---|---|

실제 항목만 넣으며 빈 예제 행을 검증된 자산으로 등록하지 않는다. 전용 폴더 안의 계약·실행 파일에는 상대 링크를, 기존 checkout의 파일에는 현재 확인한 로컬 링크와 저장소 상대경로·revision을 남긴다. checkout이 바뀌면 링크와 내용을 다시 대조한다. 원본 증거와의 대응은 선택한 저장소의 실행 결과에 보존하며 지식 저장소에는 비밀이 제거된 보고서 항목 ID를 연결한다.

사용 계약은 아래 내용을 갖춘다. 문서 필드를 Maestro YAML 명령이나 batch step의 추가 key로 넣지 않는다.

| 항목 | 기록할 내용 |
|---|---|
| 식별·파일 | 안정적인 ID, 목적/검색어, revision, 실행 파일/형식·호출법, 참조하는 하위 흐름 |
| 적용 범위 | 앱·타깃/configuration·SDK variant, 플랫폼/UI 유형, 환경, 필요한 기기 프로필, fixture/시뮬레이터/실기기 구분 |
| 입력 | 비밀이 아닌 인자와 허용값·범위. 실제 계정·세션·기기 식별자는 포함하지 않음 |
| 시작·종료 | 시작 화면/상태, 종료 표식·관측값, 이미 도착했을 때의 처리, selector 근거 |
| 영향·복구 | 바꾸는 설정/서버 자료, 원래 값 복원, 재실행 가능 여부, 부분 반영 때 확인할 사실과 중단 지점 |
| 검증 | 상태와 이유, 검증 시각·앱 빌드·OS/기기 프로필·도구 버전·입력 범위, 기대/관찰 결과, 근거 링크 |
| 내용 식별 | 검증한 실행 파일과 하위 파일 각각의 Git commit과 이후 변경 여부, 또는 SHA-256. revision 이름만으로 내용 일치를 확인하지 않음 |

선택한 부모 흐름은 참조하는 하위 흐름의 상태·내용도 확인한다. 하위 파일·selector·입력 의미가 바뀌면 영향을 받는 부모의 검증도 갱신한다. 같은 기기에서 썼다는 이유로 다른 앱이나 플랫폼용 동작을 복사하지 않는다. 공통 동작과 필요한 플랫폼별 작은 흐름을 조합한다.

실제 기기 설정·계정 참조는 기존 로컬 비공개 설정에, 원본 로그·영상·실행 결과는 선택한 저장 폴더 안에서 프로젝트·호스트의 추가 산출물 정책을 충족하는 경로에 둔다. Library의 QA 전용 폴더에는 정책·실행 소스·사용 계약·발견 지식만 저장하며 카탈로그를 실제 기기 ID나 캡처 저장소로 사용하지 않는다.

## 새로 확인한 동작을 다음 QA에 남긴다

1. 반복 가능성이 있는 새 구간은 진행 중 명령이 끝난 체크포인트에서 시작/종료 상태·허용 조작·실제 관측·근거를 모은다. 성공한 명령 몇 줄을 전체 흐름 검증으로 간주하지 않는다.
2. 같은 목적의 기존 항목을 다시 확인한다. 기존 항목 보완이면 ID를 유지하고 revision을 바꾼다. 새 항목이면 목적 단위 ID로 실행 파일과 계약을 저장하고 `draft`로 등록한다. 수정 전 검증 기록·실행 실패 이력은 남기고, 검증 중인 파일을 기존 `verified` 파일에 무조건 덮어쓰지 않는다.
3. 저장한 실행 파일과 모든 하위 흐름을 실제 대상·시작 상태에서 실행하고 종료 조건을 관측한다. 탐색 기록을 재작성·변수화·export한 파일도 실행 전에는 `draft`다. 저장 파일의 내용 식별과 실제 실행 근거를 메인이 대조한 뒤 확인한 범위만 `verified`로 기록한다.
4. 다운로드·등록·삭제·결제 등 영향을 남기는 조작을 승격만을 위해 반복하지 않는다. 허용된 다음 QA에서 저장 파일을 검증할 때까지 `draft`와 미실행 사유를 유지한다. 파일 실행·실기기·서버 반영 중 무엇을 확인했는지 구분한다.
5. 메인은 실행 담당자의 `flow_results`를 대조해 전용 저장소의 카탈로그·계약·진입점을 갱신한다. 다음 QA가 실행 파일을 실제로 찾고 열 수 있는지 링크를 확인하고 저장 경로·상태를 결과에 남긴다. 새 정책·발견 지식은 [지식 관리](project-knowledge.md)의 검토 절차로 갱신한다. 저장을 못 했으면 현재 실행의 저장 후보 위치와 미저장 사유를 인계하며 저장 완료라고 보고하지 않는다.

이미 승인 범위의 `--save-script` 기록이 있다면 이를 저장 후보로 활용한다. 기록을 시작하려고 정상 세션을 재실행하거나 종료하지 않는다. 기록이 없으면 확인한 조작을 필요한 인자·조건과 함께 파일로 작성하고, 저장 파일을 실행하기 전까지 `draft`를 유지한다.

| 상태 | 선택·관리 방법 |
|---|---|
| `draft` | 저장했지만 파일 실행·근거 확인 미완료. 승인된 QA의 검증 후보로 사용하며 검증된 재사용으로 집계하지 않음 |
| `verified` | 파일 내용과 시작/종료 조건을 근거로 확인한 범위에서 재사용 가능. 현재 시작 조건은 여전히 확인함 |
| `needs_revalidation` | 파일/하위 흐름/호환 조건 변경이나 실행 불일치가 확인된 범위. 원인과 재검증 조건을 적고 자동 재사용 대상에서 제외 |
| `retired` | 대체됨/사용 중단. 대체 ID와 이유를 남기며 자동 선택하지 않음 |

실패는 앱 결함, selector/흐름 변경, 시작 상태 불일치, 도구/기기 문제를 구분해 기록한다. 시작 상태가 다른 것만으로 모든 검증 기록을 폐기하지 않는다. 내용이나 호환성이 바뀌었는지 확인할 수 없는 범위는 `needs_revalidation`으로 남기고 독립적인 정상 범위는 보존한다.

재사용 중 실패하면 부분 실행과 마지막 확인 상태에서 본문의 복구 규칙을 적용한다. 파일의 처음부터 무조건 재실행하지 않는다. `runFlow` 내부의 부분 실행을 정확히 알 수 없으면 미확인으로 남긴다. native `replay --from`을 사용할 때는 도구가 반환한 단계·`planDigest`를 사용하고 이미 실행된 동작을 반복하지 않는다. 복구 파일·수정본은 기존 기대값과 다시 검증한 후 반영한다.

## 실행 인계와 종료 확인

- `flow_plan`에는 `catalog_path`, `search_result`, `selected`를 전달한다. `selected`의 각 항목은 `id`, `revision`, `mode`(`reuse`/`validate`), `flow_path`, `contract_path`, 비밀이 아닌 호출 인자 `arguments`이며 경로는 현재 프로젝트의 확인한 절대 경로다. 인자가 없으면 `{}`, 미확인이면 `null`로 두고 필요한 입력을 확보하기 전에는 실행하지 않는다. 후보 없음과 조건 불일치를 구분하고, 이미 조사한 검색을 담당자가 반복하지 않도록 한다.
- `flow_results`에는 구간에서 사용·관찰·저장한 각 흐름의 `id`(새 ID 미확정이면 `null`), `revision`, `action`, `condition`, `flow_path`, `contract_path`, `evidence`, `note`를 반환한다. `action`은 `reused`·`candidate`·`revalidated`·`invalidated`·`saved`다. `condition`은 본문의 `충족`·`불일치`·`확인 불가`를 사용한다. `note`에는 상태·저장/미저장 사유·부분 실행을 적는다. 경로·revision 미확인은 `null`, 근거 미확보는 `[]`와 사유로 구분한다.
- 실행 담당자는 후보·불일치 근거를 반환하며 `verified` 승격이나 업무 기대값 변경을 독자적으로 결정하지 않는다. 메인이 동일 카탈로그의 갱신을 직렬로 처리한다. `saved`는 실행 파일·계약·카탈로그 갱신이 모두 끝났을 때만 사용하고 `note`에 카탈로그 위치·자산 상태를 남긴다.
- 종료 전에 검색/선택 결과, 실제 사용한 ID·revision, 저장 파일과 근거, 갱신한 상태 또는 미저장 사유를 확인한다. 재사용 성능 개선을 주장하려면 같은 조건에서 전체 경과 시간·모델 왕복·복구 빈도를 비교하며 저장 파일 수나 명령 수만으로 효과를 단정하지 않는다.
