AI가 만든 **“거의 맞는”** 화면과 동작을 사람이 눈으로 하나씩 확인하는 대신, 실기기·iOS Simulator·Android Emulator에서 찍은 화면과 픽셀 수치로 판정하는 검증 루프를 제공합니다.

Codex와 Claude Code에서 쓰는 macOS 플러그인입니다. 지정한 실기기·iOS Simulator·Android Emulator에서 앱을 조작해 확인하고, 기준 화면과 픽셀 단위로 비교하고, 허락한 범위에서 코드를 고친 뒤 같은 조건으로 다시 찍어 리포트로 남깁니다. Simulator는 `agent-device` 없이도 기존 UI 테스트·사용 가능한 화면 제어와 `simctl` 캡처를 사용할 수 있습니다. [1], [2], [3]


## 역할별 도구 선택

[iOS Simulator·Android Emulator·Flutter 도구 선택 기준](skills/mobile-device-qa/SKILL.md#역할별-도구-선택)을 적용합니다. iOS 탐색·캡처는 `simctl`과 설치된 `xcui`/AXe·CUA, Android Emulator는 [Android CLI](https://developer.android.com/tools/agents/android-cli)와 ADB를 기본으로 사용합니다. 반복 회귀는 기존 테스트를 재사용하고, 공통 흐름이 필요할 때 [Maestro](https://docs.maestro.dev/get-started/supported-platform/flutter), Flutter와 OS·네이티브 화면 경계가 필요할 때 [Patrol](https://patrol.leancode.co/documentation/native/overview)을 추가합니다. 원본 PNG 비교와 Markdown·GIF 보고는 조작 도구와 독립적으로 유지합니다.

## 왜 필요한가요?

AI에게 화면 하나를 맡기면 대개 **거의 맞는 것**이 돌아옵니다. 목록은 뜨지만 필터 조건을 반대로 읽었고, 카드 구조는 비슷하지만 기준 디자인과 간격이 몇 px씩 다르고, 버튼은 제자리에 있지만 눌렀을 때의 결과가 요구와 다릅니다. 컴파일도 되고 화면도 열리기 때문에 빌드와 단위 테스트는 이 차이를 잡지 못합니다. 남는 것은 사람이 기기를 들고 화면을 하나씩 열어 기억 속의 기준과 맞춰 보고, “뭔가 다른데”를 말로 설명해 다시 시키는 반복입니다.

이 반복은 개인의 체감이 아니라 공개 조사에 나타난 비용입니다. 그래프 1은 응답자 49,000명 이상이 참여한 2025년 Stack Overflow 개발자 설문의 AI 항목입니다. [4]

## 무엇으로 판정하나요?

세 가지 어긋남은 서로 다른 근거로만 드러납니다. 동작의 어긋남은 실제 조작과 관찰로, 구조의 어긋남은 기준 화면과의 겹침으로, 몇 px의 어긋남은 차이 이미지와 픽셀 수치로 드러납니다. 이 플러그인은 그 근거를 만들고 판정과 함께 Markdown 리포트에 남깁니다. [1], [2]

![세 가지 어긋남이 각각 관찰·겹침·픽셀 수치로 드러나 하나의 판정으로 모인다](docs/figures/mqa-02-evidence.svg)

*그림 2. 어긋남의 유형과 그것을 드러내는 근거*

근거가 없으면 통과로 올리지 않습니다. 다른 작업이 기기를 점유했거나, 화면이 보호되어 캡처되지 않았거나, 설치된 빌드를 확인하지 못했으면 `미검증` 또는 `준비 필요`로 남깁니다. 크기나 상태가 다른 두 이미지를 자동으로 확대·정렬해 맞추지도 않습니다. 조건을 맞춰 다시 촬영합니다. [2]

코드 수정은 **사용자가 허용한 범위 안에서만** 수행하고, 수정한 뒤에는 같은 기준으로 다시 촬영해 최초 수정 전과 최종 빌드를 나란히 보여줍니다. 루프를 닫는 것은 AI의 자기 보고가 아니라 새로 찍은 화면입니다. [1]

## 사례 1. 1년 가까이 재현되지 않던 검은 화면

iPad 학습 앱에서 “소리는 나는데 영상만 검다”는 문의가 8건, “재생하면 1초 만에 멈춘다”는 문의가 26건 쌓여 있었습니다. 재설치로는 해결되지 않았고 웹 플레이어와 다른 앱은 정상이었습니다. 빌드도 테스트도 통과했습니다. 원인은 앱이 **화면에는 보이지만 입력을 받지 않는 상태**(`UIApplicationState.inactive`)를 플레이어가 백그라운드와 똑같이 취급한 것이었고, 그 판정은 1년 반에 걸쳐 다섯 개의 커밋이 조금씩 넓혀 놓은 것이었습니다.

재현이 어려웠던 이유는 조건이 겹쳐 있었기 때문입니다. 백그라운드 재생을 켜고, 제어 센터를 열어 앱을 `Inactive`로 만들고, 그 상태에서 지금 재생 중 위젯으로 일시정지 → 재생을 눌러야 합니다. 시뮬레이터에는 제어 센터가 없고, 화면을 눈으로만 보면 “검은 화면”이라는 증상 외에 아무것도 남지 않습니다.

재현 절차를 네 단계로 고정하고 나서는 나머지가 루프였습니다. 수정 전 빌드는 같은 작업 트리에서 수정 네 곳만 되돌려 만들었고(녹화 뒤 복원하고 diff로 확인), 두 빌드에 같은 진단 로그를 넣어 같은 기기에서 같은 조작을 녹화했습니다. 그림 3이 그 두 녹화입니다.

![수정 전에는 영상 영역이 약 8초간 검게 남고, 수정 후에는 같은 구간에서 영상이 계속 보인다](docs/figures/mqa-03-case.svg)

*그림 3. 사례 1의 수정 전후 비교 (실기기 녹화와 로그를 도형으로 다시 그린 것)*

*표 2. 사례 1의 실기기 확인 결과*

| 확인 | 빌드·기기 | 관찰 | 판정 |
|---|---|---|---|
| 재현 절차 | 수정 전 · iPad 8세대 | 재생 재시작 직후 영상 레이어 분리, 소리만 남음 | 재현 (무인 자동화) |

| 같은 절차 3회 | 수정 후 · iPad Pro 11 (M5) | 세 번 모두 분리 로그 0건, 영상이 계속 보임 | 통과 (녹화) |
| 앱 전환(PiP 경로) | 수정 후 · iPad Pro 11 (M5) | resign 약 0.15초 뒤 PiP 시작, 분리 없음 | 통과 |

판정 두 개가 `미검증`으로 남은 것이 이 표의 요점입니다. 수정은 네 곳을 고쳤지만 그중 한 경로는 실기기로 밟지 못했고, 26건이 접수된 쪽 증상은 수정 전 빌드에서도 끝내 재현되지 않았습니다. 리포트는 그 둘을 통과로 올리는 대신 아직 무엇을 모르는지로 남겼습니다. 재현된 쪽만 수정 전후 녹화와 로그로 닫았습니다.

사람이 눈으로 보던 루프에서 이 버그는 1년 가까이 “가끔 그런다”로 남아 있었습니다. 달라진 것은 도구가 더 똑똑해진 것이 아니라, 조건을 고정해 같은 화면을 두 번 찍고 그 차이를 남긴 것입니다.

이 사례는 비공개 저장소의 내부 수정 보고서를 요약한 것이며 화면 녹화와 코드는 포함하지 않았습니다.

## 사례 2. 내 변경이 깬 것인지 가리기

패키지 구조를 재배치하고 재생 입력 처리 순서를 바꾼 뒤 회귀 검수를 돌렸습니다. 열 개 항목이 통과하고 두 개가 실패했습니다. 그런데 이 검수는 **회귀 여부를 판정하지 않고 끝났습니다.** 변경 전 빌드로 같은 조작을 해보지 않았으니 이 실패가 이번 변경 때문인지 원래 있던 것인지 가를 수 없다고, 리포트에 그대로 적혀 있었습니다.

여기서 멈추면 “고쳐야 하나”가 남습니다. 변경 전 빌드를 같은 기기·같은 계정·같은 강의로 다시 세우는 일이 번거롭기 때문입니다. 덮어 설치할 때마다 로그인 세션이 날아가고, 추적하지 않는 로컬 설정 파일이 없으면 첫 빌드는 설정 오류 화면에서 멈춥니다. 게다가 실패 하나는 두 번에 한 번 나오는 증상이라, 몇 번 눌러 보고 “안 나는데”로 끝내기 딱 좋습니다.

두 번째 실행은 변경 직전 커밋을 별도 작업 폴더에서 빌드해 두 빌드를 함께 세웠습니다. 어느 쪽이 돌고 있는지는 실행 파일 해시로 못 박았고, 덮어 설치할 때마다 같은 계정으로 다시 로그인했습니다. 그다음 같은 좌표·같은 길이의 제스처를 두 빌드에 똑같이 반복했습니다.

*표 3. 같은 조작을 두 빌드에 반복한 결과*

| 첫 검수의 실패 | 변경 후 빌드 | 변경 전 빌드 | 판정 |
|---|---|---|---|
| 먼 구간으로 끌어 놓은 뒤 네트워크 오류 (첫 검수에서 2회 중 1회) | 두 좌표 × 5회, 오류 0건 | 두 좌표 × 5회, 오류 0건 | 두 빌드 모두 재현되지 않음. 변경과 연결할 근거 없음 |
| 구간 반복의 “끝” 버튼 무반응 | 탭 방식 5가지 모두 무반응 | 모두 같음 | 변경 전부터 있던 결함 |

둘 다 “실패”였지만 하나는 이번 작업 밖의 일이었습니다. 반복 과정에서 조건도 하나 드러났습니다. 컨트롤이 약 3초 뒤 자동으로 숨는데, 그 전에 다음 탭을 하면 버튼이 아니라 표시 전환으로 먹힙니다. 시행 앞에 4초 대기를 넣고 나서야 결과가 안정됐습니다. 손으로 눌러 보는 동안에는 이것이 “가끔 안 눌린다”로 보입니다.

## 사례 3. 화면에 없는 원인 찾기

공유 바의 세 경로가 전부 실패했습니다. 메신저 두 곳은 앱이 분명히 설치돼 있는데도 “앱 설치 필요”가 떴고, 문자는 “지원되지 않는 URL”이 떴습니다. 재설치해도, 다른 기기에서도 같았습니다.

화면에 남는 정보는 그 안내 문구뿐입니다. 셋이 같은 원인인지 다른 원인인지조차 화면으로는 알 수 없고, “앱이 없다”는 앱 자신의 주장을 반박할 재료도 없습니다. 이 상태에서 할 수 있는 추측은 대개 설치 상태나 서버를 의심하는 쪽으로 흐릅니다.

실기기 콘솔을 붙인 채로 같은 조작을 반복하자 원인이 세 줄의 로그로 갈렸습니다.

*표 4. 화면이 보여 준 것과 콘솔이 말한 것*

| 경로 | 화면 | 콘솔 |
|---|---|---|
| 메신저 A 공유 | “앱 설치 필요” | `not allowed to query for scheme` — 조회 가능 스킴 목록 58개 중 55번째라 플랫폼 한도 50을 넘겨 잘림 |
| 메신저 B 공유 | 같은 안내 + 약 5초 뒤 스토어 페이지로 이동 | 같은 한도 초과. 이동은 웹 SDK의 대체 동작 |
| 문자 보내기 | “지원되지 않는 URL” | `-1002`. 외부 스킴 판정이 그 목록만 보느라 `sms`를 빠뜨려 WebView가 직접 열려다 실패 |

한도 값은 플랫폼 공식 문서로 교차 확인했습니다. 고친 뒤 같은 기기에서 세 경로를 다시 열어 전부 통과했고, 수정 전에 나던 두 로그가 최종 실행 로그에 **한 줄도 없다는 것**까지 확인했습니다. 잘못된 안내가 남지 않는지는 화면 접근성 트리로 0건임을 매 항목 확인했습니다.

재검증을 돌리는 중에 결함이 하나 더 나왔습니다. 1차 수정본에서는 시스템 확인창을 취소하면 “앱 설치 필요”가 잘못 떴습니다. 그것도 고쳐 통과시켰습니다. 반대로 끝까지 범위 밖으로 남긴 것도 있습니다. 확인창이 떠 있는 동안 웹 SDK가 화면을 스토어 페이지로 옮기는 동작은 이쪽 코드가 아니라서 잔여 이슈로 적었습니다.

## 사례 4. “성공”과 실제로 된 것의 구분

즐겨찾기를 추가하면 처리 중 표시가 사라지지 않고, 그다음 요청은 전부 거절됐습니다. 원인은 SDK가 보내는 알림이 쓰기 결과가 아니라 **목록을 다시 읽었다는 알림**이었다는 데 있었습니다. 쓰기마다 그 알림이 온다고 가정한 코드는, 수락은 됐지만 알림이 오지 않는 경우에 영원히 기다립니다.

사람이 이걸 잡기 어려운 이유는 모든 신호가 성공이라고 말하기 때문입니다. SDK는 요청을 받아들였다고 답하고, 로그에도 실패가 없습니다. 화면만 “조금 느린” 것처럼 보입니다. 확인하려면 추가하고, 화면을 나갔다 다시 들어오고, 하나만 지우고, 또 들어와 보는 흐름을 실기기에서 끝까지 돌려야 하며, 매번 만든 데이터를 원래대로 돌려놔야 합니다.

*표 5. 흐름 전체를 돌린 결과*

| 확인한 것 | 결과 |
|---|---|
| 추가 → 연속 추가 → 재진입 → 개별 삭제 → 나머지 삭제 → 삭제 후 재진입 | 여섯 단계 모두 통과. 검증하느라 만든 항목 2개는 0개로 복구 |
| 완료 토스트의 순간 표시와 정밀 반영 시간 | 미검증 — 캡처 지연 때문. 정지 화면을 이어 붙여 연속 동작의 근거로 삼지 않음 |
| 라벨 수정 | 미검증 — 텍스트 입력 연결이 복구되지 않음 |

도중에 조작 도구가 연결 오류를 반환한 적이 있습니다. 그런데 화면에는 항목이 이미 추가돼 있었습니다. 이때 명령을 다시 보내지 않고 화면으로 결과를 확인했습니다. **도구가 실패한 것과 앱이 실패한 것은 다른 일**이고, 재전송했다면 중복 데이터가 생겼을 것입니다.

리포트에는 성공의 범위도 적었습니다. “여기서 성공은 요청 수락과 목록 반영까지이며, SDK 내부 비동기 작업이나 서버 저장 완료를 보장하지 않는다.” 확인한 만큼만 주장하는 것도 결과의 일부입니다.

네 사례가 공통으로 보여 주는 것은 사람의 실력이 아니라 근거의 위치입니다. 콘솔 한 줄, 변경 전후 두 빌드, 흐름 전체를 열 번 반복하기, 조건을 맞춰 두 번 찍기 — 전부 할 수는 있지만 매번 하기엔 번거로운 일이고, 그래서 보통은 건너뜁니다. 루프는 그걸 매번 합니다.

## agent-device로 어떤 워크플로우를 만들었나요?

`agent-device`는 별도로 설치하는 기기 조작·조회·증거 수집 도구입니다. **Mobile QA는 그 기능에 프로젝트별 검증 조건, 판정 기준, 수정 후 재검수, 흐름 저장과 리포트를 연결합니다.** 아래 표는 원도구의 기능과 이 플러그인이 조합한 워크플로우의 관계입니다. [1], [2], [8]

| agent-device가 제공하는 기능 | Mobile QA가 연결한 워크플로우 | 받는 결과 |
|---|---|---|
| 화면 요소 조회와 터치·입력·스크롤, 조건 대기·검증 (`snapshot`, `press`, `fill`, `wait`, `is`) | 현재 화면에서 대상을 찾고, 조작 뒤 기대 상태를 확인하는 기능 QA | 항목별 기대값·관찰·판정과 스크린샷 |
| 앱 실행·딥링크·홈 이동·회전·시스템 알림 조작 (`open`, `home`, `orientation`, `alert`) | 지원되는 조건에서 앱 진입·복귀·회전·권한 창 흐름 검증 | 조건별 관찰과 실패 단계 |
| 스크린샷과 녹화 (`screenshot`, `record`) | 같은 조건으로 촬영하고, 별도 이미지 비교 도구로 기존 앱·Figma와 비교한 뒤 허용된 코드를 수정·재촬영 | 겹침·차이·픽셀 수치, 최초 수정 전 / 최종 수정 후 비교 |
| 로그·네트워크 정보·성능 자료 (`logs`, `network`, `perf`, `trace`) | 재현 조작과 필요한 실행 근거를 연결해 원인을 좁히고, 성능은 별도 지표로 확인 | 재현 절차, 로그·계측 자료, 확인 범위와 남은 미검증 |
| 연속 실행·기록 재생·테스트 묶음 (`batch`, `replay`, `test`) | 검증한 흐름을 재사용하고, 수정 전후 빌드에서 같은 조건으로 회귀 확인 | 반복 실행 결과와 실패 단계, 다음 QA가 찾을 실행 파일·사용 조건 |
| 기기·세션 선택과 지원 기능 조회 (`devices`, `session`, `capabilities`) | 프로젝트·설치 빌드·기기를 고정하고, 기존 세션 재사용과 제어권 인계 | 어느 빌드·기기에서 확인했는지 추적할 근거 |

이미지 비교는 이 플러그인의 Python 도구가, Figma 기준 이미지 내보내기는 연결된 Figma 도구가 담당합니다. 계정은 별도 `test-accounts` 스킬로 저장·조회하고, AI가 읽은 계정값을 일반 기기·브라우저 입력 도구에 전달해 로그인합니다. 코드 수정·빌드는 호스트 에이전트가 프로젝트 절차로 수행하고, 준비된 앱의 설치는 지원되는 도구로 수행합니다. `agent-device` 자체가 소스를 수정·빌드하는 것은 아닙니다. [2], [3]

기능 QA에는 Figma가 필요 없습니다. 이미 로그인된 세션이면 계정 도구도 필요 없고, PNG 두 장만 비교할 때는 기기와 `agent-device` 없이 이미지 비교 도구를 사용할 수 있습니다. 세부 명령과 여섯 가지 워크플로우는 [운영 레퍼런스](docs/operations.md#agent-device의-기능과-플러그인의-역할)에 있습니다.

**iOS Simulator QA도 지원합니다.** [Simulator 절차](skills/mobile-device-qa/references/simulator.md)에 따라 `simctl`로 원본 PNG·영상을 확보하고 기존 비교 도구로 디자인 검수와 Markdown 리포트를 작성합니다. 자동 UI 조작 경로가 없으면 필요한 화면 이동만 사용자에게 요청하고 캡처·비교·보고는 계속합니다. Simulator에서 확인한 결과는 실기기 결과와 구분합니다.

## 할 수 없는 일은 무엇인가요?

- **실기기의 실제 소리·진동·물리적 연결을 단독 검증:** 스피커·이어폰 출력이나 케이블 탈착 등에는 사람 또는 별도 장비가 필요합니다. `audio probe`는 브라우저·호스트에서 출력되는 가상 기기 오디오가 대상입니다.
- **모든 통신 수집·응답 변조와 서버 저장 확정:** `network`는 앱 로그에 남은 HTTP(S) 정보를 읽습니다. 누락된 통신, 응답 조작, 실제 서버 저장은 프록시·테스트 서버·재조회 같은 별도 근거가 필요합니다.
- **OS 보안·DRM 우회와 모든 시스템 화면 재현:** 보호된 영상은 검게 캡처될 수 있고, XCTest가 붙여넣기를 자동 허용해 iOS의 허용 팝업을 시험할 수 없는 경우도 있습니다.
- **화면 일치나 녹화만으로 성능·전체 기능 보장:** 녹화 FPS는 앱의 렌더링 성능이 아닙니다. 보지 않은 상태·기기·내부 처리까지 통과로 확장하지 않으며, 간헐적 버그의 재현도 보장하지 않습니다.
- **원도구의 모든 대상을 같은 수준으로 지원:** 이 플러그인의 기기 QA 경로는 iPhone·iPad·Android 실기기, iOS Simulator, Android Emulator를 포함합니다. Flutter는 실행 대상 플랫폼의 경로를 사용합니다. 원도구의 macOS·TV·웹·원격 기능 전체나 모든 Maestro 문법을 지원 범위로 포함하지 않으며, Simulator 결과로 실기기 동작을 보장하지 않습니다.

위 한계와 별도 검증 방법은 [운영 레퍼런스](docs/operations.md#할-수-없는-일과-별도-검증이-필요한-일)에 구분했습니다. 도구가 지원하는 기능과 특정 기기에서 실제 확인한 결과는 다릅니다. [1], [8]

다른 도구와 조합하면 준비·관찰 범위를 확장할 수 있습니다. **Mac Computer Use로 이미지를 AirDrop → 기기에서 도착 확인 → agent-device로 앱에 가져오기**를 비롯해 USB 파일 준비, 웹·모바일 동기화, 실제 푸시, 통신 장애, QR/OCR·오디오와 업데이트 시험을 [확장 워크플로우 후보](docs/workflow-extensions.md)에 정리했습니다. 필요한 도구·검증 범위·정리 방법을 함께 적었으며, 이 조합들은 아직 실기기에서 검증된 플러그인 흐름이 아닙니다.

## 시작하기

쓰는 호스트에 플러그인을 설치합니다.

```bash
# Codex
codex plugin marketplace add https://github.com/Jimmy-Jung/mobile-qa.git
codex plugin add mobile-qa@mobile-qa-marketplace
```

```bash
# Claude Code
claude plugin marketplace add Jimmy-Jung/mobile-qa
claude plugin install mobile-qa@mobile-qa-marketplace --scope user
```

처음 한 번 `setup`으로 결과를 저장할 폴더를 고릅니다. Claude Code는 `/mobile-qa:setup`, Codex는 설치된 setup 스킬입니다. 내장이든 외장이든 이미 있는 폴더를 고르면 되고, 다음부터는 같은 폴더를 확인해 다시 씁니다.

그 다음에는 프로젝트와 기기, 확인할 내용을 알려주고 요청하면 됩니다.

> mobile-device-qa로 지금 checkout과 연결된 Android 시험 기기를 확인해줘. 로그인 세션은 그대로 두고, 목록 열기 → 상세 진입 → 목록 복귀 때 고른 필터가 유지되는지 봐줘. 항목별 결과와 스크린샷, 대표 조작 GIF를 리포트로 만들어줘.

> mobile-device-qa로 지정한 iOS Simulator에서 이 앱을 검수해줘. agent-device 없이 사용 가능한 UI 테스트나 화면 제어와 simctl 캡처를 사용하고, Figma와 디자인을 비교해 스크린샷·겹침·차이·동작 GIF가 포함된 Markdown 리포트를 작성해줘. 필요한 직접 로그인만 요청하고 Simulator에서 확인한 범위를 표시해줘.

> 첨부한 Figma 프레임을 기준으로 지정한 iPhone의 새 빌드를 검수해줘. 같은 크기·배율·테마·폰트·데이터로 찍고 겹침과 차이 이미지로 어긋난 곳을 찾아줘. 관련 UI 코드까지 고치고 다시 빌드해서 같은 조건으로 재촬영해줘.

더 많은 요청 예시와 준비물은 [운영 레퍼런스](docs/operations.md)에 있습니다.

## 결과물

기본 결과물은 리포트 한 장(`report.md`)과 거기에 붙는 이미지·GIF입니다. 따로 볼 앱이 필요 없고, 옮길 때는 리포트와 첨부물을 함께 옮기면 됩니다. 디자인 검수를 하면 겹침 이미지와 차이 이미지, 픽셀 수치를 담은 비교 파일이 함께 생깁니다.

판정은 네 가지입니다.

- `통과` — 명시한 기기와 빌드에서 기대한 대로 동작하는 것을 근거로 확인했습니다.
- `실패` — 기대와 다른 관찰과 그 근거가 있습니다.
- `미검증` — 실행하거나 관찰한 근거가 모자랍니다. 이유와 다음에 확인할 것을 함께 적습니다.
- `준비 필요` — 도구·빌드·권한·화면 조건을 먼저 갖춰야 합니다.

겹침 이미지의 밝기나 차이 영역의 넓이만으로 원인을 단정하지는 않습니다. 크기나 상태가 다른 두 이미지를 자동으로 늘리거나 맞춰 비교하지도 않습니다. 조건을 맞춰 다시 찍습니다. 파일 이름과 수치를 읽는 방법은 [예시 리포트](examples/design-review/report.md)에 실제 출력으로 나와 있습니다.
