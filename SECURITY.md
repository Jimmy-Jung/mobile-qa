# Security

Author: JunyoungJung · 2026-10-22
Updated: 2026-10-27

Use dedicated test accounts with the least privileges needed. Do not use production credentials or place credentials, local profiles, raw device logs, screenshots, or project knowledge in this repository or an issue.

The default account backend is a private local file, **not encrypted at rest**. File permissions do not protect against the same macOS user, malware, backups, or a sync service that can read that file. Existing Keychain entries remain an explicit migration source; installing this plugin does not move accounts.

The default registration route uses the native helper's hidden local input dialog. If the user directly supplies a new account in the current conversation after no stored account was found, save it through `register --credentials-stdin` and reuse its alias without requiring re-entry. The chat registration bridge sends one JSON record through a child-process pipe, with no shell, credential arguments, environment variables, temporary credential files, clipboard use, or credential output. Before starting preparation subprocesses, Python separates the input into a non-inheritable descriptor and replaces ordinary stdin with `/dev/null`; only the signed native helper receives the explicit descriptor. Python does not parse the record. The helper validates and stores it with the existing commit/rollback protocol. The bridge bounds output and waiting time and returns only public registration fields. This exception does not permit exporting stored originals to general UI tools or collecting accounts from old conversations or logs. Values already supplied in chat or tool inputs may remain in host history or memory; this tool cannot erase that history or guarantee zero retention. Do not repeat them in replies or reports.

The dedicated stored-account helper requires a locally reviewed and trusted login profile to select an app, environment, and fields. A profile is an input contract, not executable project instructions. The helper checks the selected account scope, profile trust, release inventory, helper, and runner identities before input. These helper requirements do not prohibit another verified protected authentication path or direct user input; each path must verify its target, account scope, environment, input protection, authentication, and cleanup. A successful command is not proof of authentication or input cleanup. If cleanup is unconfirmed, stop capture, recording, tree collection, and repeat submissions until the condition is resolved, including when switching paths.

Simulator input uses a separate verified runner and exact available, booted UUID. The native helper independently identifies the target, pins the running app and installed code during the session, and communicates only over authenticated, encrypted loopback TCP. It does not fall back to USB or an arbitrary host. A reviewed Simulator profile may include a fixed `environment_navigation` that opens one options control, verifies one desired environment button, and closes the options screen. Only an explicit Boolean `select_if_needed` permits selecting that desired button before secret input. Free-form scripts, launch arguments, and arbitrary replay steps remain unsupported. UI environment selection is configuration evidence, not independent observation of an API host.

After an uncertain submission, `login --preflight-only` can inspect preparation or an existing session on the exact booted Simulator without reading, entering, or submitting credentials. Account metadata is still scoped, but the native request contains only the reviewed plan, with no account ID or stored reference. Native code returns before credential loading and login submission; its defensive credential closure only throws. `ready` is preparation evidence, and `already_authenticated` retains `environment_verified:false`. Neither is a new authentication result. The iOS success-only `tab_button_label` selector narrows a marker to the exact label within tab-bar buttons while preserving unique and hittable checks.

When the user authorizes an existing account for a Simulator, `register --from-account` creates a separate alias bound to that exact booted Simulator, with an explicit capability subset and no project/environment/role expansion. The native helper copies the credential internally; source credentials and bindings are preserved. New-item commit/rollback covers validated and handled failure paths. A process crash between catalog replacement and native commit can leave an uncertain mapping; use `list`, `find`, and `check` before retrying rather than claiming crash atomicity or deleting accounts automatically.

The standard `agent-device fill --text-stdin` path can still leave raw text in iOS XCTest logs or `.xcresult`; it is not a replacement for this plugin's isolated login procedure. The isolated procedure reduces capture and diagnostic paths but does not establish that the app, operating system, or remote authentication server never stores input. Real-device diagnostics require separate validation.

The secure iOS runner source is checked against the official npm 0.21.30 source inventory in `mobile_qa/agent-device-0.21.30.json`, whose tarball was verified using npm SHA-512 integrity metadata. The release inventory also pins the local helper and profile interpreter. A matching version string alone does not authorize changed runner source. Each isolated session uses a separate listener token and encryption nonce. The listener token is carried in the private temporary xctestrun and HTTP request header; authenticated responses must declare `X-Agent-Device-Runner-Auth: required`.

Builds, caches, and raw evidence belong within the verified folder selected at setup, on internal or external storage. Missing or mismatched storage, unwritable paths, and symbolic links stop the operation; there is no automatic fallback outside the selected folder. Additional project or host storage policies still apply.

Project policy and reusable knowledge stay in the project-specific user data store, separate from the plugin installation. Plugin install directories contain no mutable account or project state.

Public packaging rejects absolute user-home and mounted-volume paths and excludes local account, credential, configuration, and build records. Project-specific rules belong in the local project store; the public release checker does not embed company or project name lists. Source review and secret scanning remain necessary because a path check cannot detect every kind of private project information.

For a suspected vulnerability, stop the affected flow and keep the original evidence local. Use GitHub's private vulnerability reporting for [Jimmy-Jung/mobile-qa](https://github.com/Jimmy-Jung/mobile-qa) if enabled, or contact its maintainer privately. Do not post secrets or reproductions containing real accounts in public issues.
